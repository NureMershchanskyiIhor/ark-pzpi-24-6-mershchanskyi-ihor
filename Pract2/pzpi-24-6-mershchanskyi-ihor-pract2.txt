2. Завдання
     Мета: навчити студентів основним методам рефакторинґу коду, ідентифікації проблем в коді та використанню конкретних методів рефакторинґу для покращення його якості.
     Рефакторинґ це модифікація вже існуючого коду для покращення його читабельності, можливості повторного використання, продуктивності, розширюваності та зручності підтримки [4].
     Погано написаний код витрачає години розробників на те, щоб зрозуміти лише як працює та для чого потрібна якась змінна. Спагеті-код уповільнює ознайомлення для нових розробників.
     Після деплою – випуску проєкту – програмне забезпечення живе довго. Набагато довше, ніж тривала його розробка. Змінюються вимоги, залежності, команди та середовище виконання. Рефакторинґ та чистка коду критично важливі аспекти підтримки системи, зберігання її зрозумілою та гнучкою, не змінюючи зовнішньої поведінки.
     Звичайні користувачі зазвичай на бачать внутрішній код системи. Його читають, змінюють та підтримують розробники. І рефакторинґ спрямований саме на них. Для користувача не з’являється нічого нового, не змінюється зовнішня поведінка. Рефакторинґ змінює лише внутрішню структуру коду.
     Ця доповідь про деякі методи рефакторинґу. Як писати код, який не потрібно переписувати. Що таке запахи коду? Яка роль модульних тестів під час рефакторинґу? Та інше.


3. Опис виконаної роботи
     Метою рефакторинґу є прибирання «запахів коду» (роздуті класи, дублювання, довгі списки параметрів та інше). Рефакторинґ потрібно робити постійно. Це не одна дія, а постійний процес. Раннє втручання у внутрішню структуру коду привчає писати чистіший код одразу, дозволяє тримати системи у готовому до здачі стані та дешевше за переписування з нуля.
     Рефакторинґ не можна починати, якщо програма не виконує свою роботу. Спочатку виправлення багів – потім краса та гармонія. Також краще зупинитися, коли починається нескінченне перетворення заради покращення (так звана «гра у перфекціоніста» – коли на це витрачається більше часу, ніж на розвиток коду). Або коли код настільки забруднено, що легше переписати все з нуля.
     Головним правилом безпечного рефакторинґу є покриття коду тестами. Це страховка на випадок зламу працюючого функціоналу. Без тестів, або якщо вони червоні, не можна починати рефакторинґ. Після зміни одного методу потрібно запускати тести, щоб нічого не зламати.
3.1. Replace Constructor with Factory Method
     Заміна конструктора фабричним методом це паттерн рефакторинґу та проєктування. Він відноситься до породжуючих паттернів – паттернів, які відповідають за полегшення створення нових об’єктів. Його суть в заміні складних, заплутаних або обмежених конструкторів класу на статичні методи (фабричні класи), які повертають екземпляр цього класу.
     У звичайному підході для створення екземпляру класу викликається конструктор напряму. Зі збільшенням кількості умов, параметрів та залежностей в логіці ініціалізації об’єкта починаються проблеми: важко зрозуміти різницю між різними варіантами створення об’єкта, бо конструктори мають фіксовану назву, а також конструктор повинен повертати новий екземпляр цього класу, а не підкласу.
     У фабричному методі створюється абстрактний клас – творець (Creator), який реалізує загальну бізнес-логіку створення об’єктів. Самі класи цих об’єктів йому невідомі. У цьому класі оголошується фабричний метод.
     Від абстрактного творця наслідуються фабрики, які перевизначають фабричний метод під себе, свою логіку, щоб він створював і повертав конкретний об’єкт певного класу.
     Останніми в цій схемі є продукти – об’єкти, які створюються фабриками. Це різні підкласи від одного спільного інтерфейсу або базового класу.
     Замість викликів з конструктором, в клієнтському коді використовуються виклики цього фабричного методу зі зрозумілою назвою. В результаті базовий клас описує, що потрібно зробити з об’єктом, але сам його не створює.

Рисунок 3.1.1 – Схема паттерну рефакторинґу «Фабричний метод»
(згенеровано за допомогою Gemini)

class Truck:
    def deliver(self):
        return "Delivery overland by truck."

class Ship:
    def deliver(self):
        return "Delivery by ship by sea."

class Logistics:
    def plan_delivery(self, transport_type: str):
        if transport_type == "truck":
            transport = Truck()
        elif transport_type == "ship":
            transport = Ship()
        else:
            raise ValueError("Unknown type of transport")
        
        result = f"Logistics Cooperation: {transport.deliver()}"
        return result

logistics = Logistics()
print(logistics.plan_delivery("truck"))
print(logistics.plan_delivery("ship"))

from abc import ABC, abstractmethod

class Transport(ABC):
    @abstractmethod
    def deliver(self) -> str:
        pass

class Truck(Transport):
    def deliver(self) -> str:
        return "Delivery overland by truck."

class Ship(Transport):
    def deliver(self) -> str:
        return "Delivery by ship by sea."


class LogisticsCreator(ABC):
    @abstractmethod
    def create_transport(self) -> Transport:
        pass

    def plan_delivery(self) -> str:
        transport = self.create_transport()
        return f"Logistics. {transport.deliver()}"


class RoadLogistics(LogisticsCreator):
    def create_transport(self) -> Transport:

class SeaLogistics(LogisticsCreator):
    def create_transport(self) -> Transport:


def example(creator: LogisticsCreator):
    print(creator.plan_delivery())

print("Use of ground logistics:")
example(RoadLogistics())

print("\nUse of maritime logistics:")
example(SeaLogistics())

3.2. Replace Error Code with Exception
     Програмісти попереднього століття, минула школа використовували коди помилок у разі помилок заліза, користувача та введення даних, а також логічних та математичних помилок. Це було основним методом повідомити користувача про нештатну ситуацію. Таке рішення оптимальним для заліза, але жахливим для людей та надійності. Це був вимушений крок. Компроміс.
     Головними проблемами комп’ютерів тієї пори були обмеження пам’яті комп’ютерів – повільні процесори та шини даних, та пристроїв виведення.
     Оперативна пам’ять вимірювалася в кілобайтах. Текстове повідомлення про помилку займає набагато більше байт, ніж числовий код помилки. А система повинна була зберігати сотні варіантів помилок. Зашити в пам’ять магічні числа було банально простіше. Розробники економили кожен байт.
     Тогочасні комп’ютери якщо і мали монітори, то вони були маленькі. Комп’ютер не міг вивести довгий опис проблеми – довге повідомлення не поміщалося. Використання коротких числових кодів заощаджувало пам’ять і екранне місце, а системний адміністратор шукав цей код у інструкції до програми.
     Ще однією проблемою було відсутність класів помилок та ієрархії винятків. Вони з’явилися лише наприкінці 80-х років разом з ООП, коли програми стали величезними, а системи повинні були працювати.
     З появою мов програмування високого рівня, таких як Java, C#, Python, у другій половині 1990-х років, комп’ютери стали потужніше, а вимоги до чистоти коду підвищилися. У того часу розробники почали активно використовувати exception-класи.
     У сучасному програмування якщо виникає проблема, Ви викидаєте помилку, яку потім перехоплює один з обробників винятків. Для реагування активується спеціальний код обробки помилок, який ігнорується за нормальної поведінки [10].

def safe_divide(a, b) -> (float, int):
    if (
        not isinstance(a, (int, float))
        or not isinstance(b, (int, float))
    ):
        return None, 2 # invalid data type
    
    if b == 0:
        return None, 1 # division by zero
        
    return a / b, 0 # success

result, code = safe_divide(10, 0)

if code == 0:
    print(f"Result: {result}")
else:
    print(f"Error: Code {code}")

def safe_divide(a, b):
    if (
        not isinstance(a, (int, float))
        or not isinstance(b, (int, float))
    ):
        raise TypeError("Arguments must be numbers")
    
    if b == 0:
        raise ZeroDivisionError("Division by zero")
        
    return a / b

try:
    result = safe_divide(10, 0)
    print(f"Result: {result}")
except ZeroDivisionError as e:
    print(f"Error: {e}")
except TypeError as e:
    print(f"Error: {e}")
Рисунок 3.2.2 – Код після рефакторинґу з використанням винятків [10]

     Майже для всіх сучасних ООП мов програмування використання винятків замість кодів повернення є стандартом. Головна перевага перших у тому, що вони відокремлюють логіку обробки помилок від бізнес-логіки, тим самим роблячи код чистішим. Винятки неможливо ігнорувати – якщо виняток не обробити, він повертається вгору по стеку, якщо його ніхто не спіймає – програма завершиться аварійно. Винятки дозволяють писати чистий код без розгалужених конструкцій if-else, які заважають читати та розуміти код. Також винятки це єдиний спосіб заборонити створення неправильного об’єкта всередині конструктора, бо він не має типу повернення.
3.3. Replace Exception with Test
     Рефакторинґ шляхом заміни виключення перевіркою застосовується тоді, коли програма використовує механізм винятків (блоки try-catch) для керування нормальним та передбачуваним потоком виконання, замість завчасної перевірки умови.
     Винятки створені для обробки непередбачуваних ситуацій. Використання їх для контролю бізнес-логіки (перевірки виходу на межі масиву або наявності ключа у словнику) це антипатерн, який призводить до забруднення коду та падіння продуктивності. Багато складних конструкцій try-catch заважають читати програми. Генерація винятків змушує систему формувати stack trace – послідовність викликів функцій або методів, які були активними в момент виникнення виключення. Це потребує набагато більше ресурсів, ніж блоки if-else.
     Отже мета рефакторинґу шляхом заміни винятків перевірками оптимізація та очищення коду. Але не треба застосовувати цей метод до всіх блоків try-catch.

class UserNotFoundError(Exception):
    pass

def get_user_permissions(user_id, permissions_db):
    try:
        return permissions_db[user_id]
    except KeyError as e:
        raise UserNotFoundError(f"User {user_id} does not exist") from e

     Умовні конструкції if-else виконуються миттєво на рівні процесора. Генерація винятків вимагає виділення пам’яті під об’єкт помилки та побудови стека викликів. В циклах або часто викликаних методах це створює значний overhead. Винятки варто знову почати використовувати лише для дійсно позаштатних ситуацій, а бізнес-логіку керувати стандартними умовами.


4. Висновки
     У ході виконання роботи було досліджено та структуровано розписано такі методи рефакторинґу коду, як фабричний метод, заміна кодів повернення винятками та використання попередніх перевірок (guard clauses) замість винятків. Було описано мету застосування таких методів рефакторинґу, випадки використання кожного з цих методів: коли їх доцільно та не варто використовувати. Їхні переваги та недоліки. До деяких було створено графічне зображення, що ілюструє процес виконання коду програмою.
     Отримано та вдосконалено навички рефакторинґу, ідентифікації проблем в коді та використанню конкретних методів рефакторинґу для покращення його якості у різних ситуаціях під час реалізації систем або читання вже написаного кимось (або чимось) коду.
