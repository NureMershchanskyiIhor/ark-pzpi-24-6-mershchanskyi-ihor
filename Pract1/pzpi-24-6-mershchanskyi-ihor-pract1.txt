2. Завдання
     Мета: ознайомити студентів з основними рекомендаціями щодо написання чистого, ефективного та підтримуваного коду для різних мов програмування, а також навчити аналізувати та рефакторити код для покращення його якості.
     Для виконання практичного завдання було обрано мову програмування C++, для якої будуть досліджені рекомендації для написання якісного та чистого коду.
     Такі узгодження не є «законами» написання коду, але для гарного тону та за відсутності зовнішніх обмежень їх доцільно використовувати. Оскільки більшу частину часу розробники витрачають на читання та аналізування вже написаного кимось коду, зберігання, особливо в масштабних проєктах, тисяч рядків в одному стилі полегшує роботу інженерів програмного забезпечення. 
     Угоди про кодування встановлюють не лише рекомендовану кількість пробілів чи табуляції, а й регулюють правила найменування, структури коду, обробки помилок, використання парадигм програмування (ООП, функціональне), оптимізації продуктивності, тестування та документування коду, а також багато інших нюансів. Це запобігає появі нових помилок.
     Проходячи повз Code Convention, з часом команда розробників великого проєкту перетворює його на «спагеті-код», коли файли написані в різному стилі. Це приводить до сповільнення написання та оновлення коду, конфліктів у команді та технічного боргу.


3. Опис виконаної роботи
3.1. Іменування сутностей
     Опис: дотримання єдиного стилю найменування класів, функцій, змінних та констант робить код самодокументованим та легким для розуміння та сприйняття.
     Узгодження щодо найменування корисні. Вони мінімізують суперечки за стиль написання коду. Таких стилів існує багато, і розробники їх полюбляють.
     У сучасному C++ зазвичай використовують стиль PascalCase для типів даних, camelCase для методів і функцій, snake_case для звичайних змінних та UPPER_SNAKE_CASE для константних змінних та макросів. Приватні змінні членів класу мають постфікс у вигляді нижнього підкреслення «_», але не треба ставити нижнє підкреслення (або два таких підкреслення) на початку назви: такі префікси зарезервовані у системних функціях. Якщо змінна (звичайна чи константа) глобальна, то рекомендовано додати префікс «g_».
     Потрібно враховувати контекст, у якому буде використовуватися ім’я. Воно має бути описовим, але не надлишковими. Гарне ім’я пояснює, що саме зберігає змінна та для чого вона потрібна, але при цьому не містить зайвих, зрозумілих, деталей. 
     Не треба часто використовувати скорочення та акроніми видалянням літер всередині слова. Скорочення краще писати з великої літери, як одне слово.
     Назви файлів треба називати у стилі camelCase, snake_case або kebab-case, в залежності від узгодженості в команді. Часто перевагу надають нижньому підкресленню та стилю snake_case.
Назви лічильників (enum) рекомендовано називати у стилі PascalCase, як і функції.
     Приклад коду:
     
#include <string>

enum Statuses {
    Ok = 1,
    Error = 2
};

class UserAccount {
public:
    static constexpr int MAX_LOGIN_ATTEMPTS = 3;
    
    UserAccount(std::string username) : username_(std::move(username)) {}
    
    std::string getUsername() const {
        return username_;
    }

private:
    std::string username_;
    int login_attempts_ = 0;
};

3.2. Форматування та стиль
     Опис: форматування відповідає за візуальну чистоту коду та знижує когнітивне навантаження на того, хто читає код.
     Форматування та стиль кодування не так важливі в контексті рефакторинґу, бо читати та розуміти код один одного легше, якщо всі розробники будуть використовувати однаковий стиль.
     Сьогодні замість пробілів бажано використовувати табуляцію. Де-факто за стандартом одна табуляція замінює 4 пробіли, але бувають випадки, коли розробники замінюють її на 2 пробіли, як, наприклад, робить та рекомендує робити Google у своєму посібнику зі стилю [1].
     Щодо розташування фігурних дужок, найпопулярніші два стиля: Allman (або BSD), коли відкриваюча дужка переноситься на новий рядок (див. рис. 3.2), який вважають читабельнішим за другий та K&R (на честь авторів мови програмування C та їх всесвітньо відомої книги «The C Programming Language»), де дужка залишається на тому ж рядку, де й конструкція (див. рис. 3.3), економлячи вертикальне місце. У мові C++ частіше використовують другий стиль – K&R, який рекомендує використовувати Google [1].
     Довжину рядка зазвичай обмежують 80, 100 чи 120 символами, щоб код поміщався на екрані без необхідності гортати горизонтально. Рядок може вміщувати і більше символів, коли це необхідно. Наприклад, коли коментар не можна розділити без втрати читабельності, якщо рядок містить приклад команди; шлях до файлу чи регулярні вирази або посилання та інші випадки. 
     Ліміт саме у 80 символів залишився з часів перфокарт та старих моніторів, коли за стандартом перфокарти мали 80 колонок, кожна з яких зберігала один символ, та екрани більшості комп’ютерів 1970-80-х років мали роздільну здатність 80 символів в ширину. Ще однією причиною є те, що людське око погано фокусується на довгих рядках тексту та комфортно сприймає текст такої ширини. 
     Приклади коду:

#include <iostream>

{

    {

    {
        std::cout << “Is number ” << i << “ even: ”

    return 0;
}

3.3. Структура коду та заголовочних файлів
     Опис: організація структури коду та заголовочних файлів є одним з найважливіших аспектів Code Convention. Неправильна структура може привести до уповільнення компіляції, циклічних залежностей та хаосу у коді.
     Головним правилом є розділення інтерфейсу та реалізації:
* файли заголовків (.h або .hpp) повинні містити оголошення класів, функцій та структур;
* файли реалізації (.cpp) – код (визначення функцій та методів).
     Винятком є шаблонні класи та inline функції, які потрібно повністю реалізувати в заголовочних файлах, оскільки компілятор потребує їхній повний код у момент створення екземпляру шаблону.
     Для захисту від повторного включення файлів в сучасному коді використовують директиву #pragma once замість класичних #ifdef та #define.
     Рекомендується групувати підключення заголовочних файлів від специфічних до загальних за таким порядком:
* заголовочний файл поточного cpp (часто з такою самою назвою, як файл з кодом, тільки розширення .h або .hpp);
* заголовочні файли проєкту;
* сторонні бібліотеки (Boost, OpenSSL та інші);
* стандартні бібліотеки C++ (<iostream>, <vector>, <string> та інші);
* системні бібліотеки C.
     Це допомагає виявити приховані залежності.
     Також всередині класу рівні доступу реалізуються за такою послідовністю: public, protected, private.
     Приклад коду:

#pragma once

class Calculator {
public:
    int add(int x, int y);

    int subtract(int x, int y);

    int multiply(int x, int y);

    int divide(int x, int y);
};

3.4. Парадигми програмування
     C++ це мультипарадигмова мова програмування. Тобто, вона підтримує кілька стилів написання коду. Щоб код був безпечний, швидкий і підтримуваний, рекомендовано регулювати не тільки іменування та форматування, а й такі парадигми програмування, як процедурна (імперативна), ООП, узагальнене та функціональне програмування. Код написаний мовою C++ поєднує кілька основних парадигм.
     Сучасна розробка на C++ зазвичай поєднує три головні парадигми:
* процедурний підхід у стилі C для простих функцій, оптимізації на низькому рівні та математичних обчислень;
* ООП для побудови архітектури системи та моделювання складних сутностей;
* узагальнене програмування для написання коду, що працює з будь-якими типами даних без втрати швидкості.
3.4.1. Процедурна (імперативна) парадигма
     Класичним підходом є процедурна або імперативна, який включає послідовність викликів функцій, глобальні чи локальні змінні та цикли. В такому стилі програміст в коді описує послідовність кроків, які потрібно виконати для досягнення результати. Часто велику програму розбивають на підпрограми, процедури чи функції, що забезпечує модальність.
     Перевагами такого підходу є зрозумілість – логіка відповідає ходу виконання процесором, тобто читач коду розуміє алгоритм, який виконує процесор; висока продуктивність, бо розробник контролює ресурси пам’яті та апаратне забезпечення; а також уникнення дублювання коду завдяки використанню функцій.
     Недоліками ж є складність у підтримці великих проєкті через збільшення процедур та зовнішніх змінних, що ускладнює відстеження коли та яка частина змінила дані. Коли проєкт розростається, розуміти код стає складніше через велику кількість технічних деталей, таких як декларація змінних, виділення пам’яті та інші. Людина, яка читає код, бачить лише алгоритм розміщення та передавання байтів у пам’яті замість мети програми.
     Ці мінуси змусили трансформувати більшість мов програмування у мультипарадигмові, серед яких Python, JavaScript, C++, C#, Java та інші. Таке перетворення дозволило використовувати імперативний стиль з його ефективністю та швидкістю, там, де це потрібно, але також застосовувати можливості функціонально чи ООП, щоб мінімізувати недоліки.

#include <iostream>
#include <vector>

constexpr int BONUS_LIMIT = 50;

int calculateTotalScore(const std::vector<int>& scores) {
    int totalScore = 0;
    
    for (int score : scores) {
        if (score > BONUS_LIMIT) {
            totalScore += score * 2;
        } else {
            totalScore += score;
        }
    }
    return totalScore;
}

int main() {
    const std::vector<int> userScores = {30, 60, 45, 80};
    
    std::cout << “Total scores: “ << calculateTotalScore(userScores) << “\n”;
    return 0;
}

3.4.2. Об’єктно-орієнтоване програмування
     Об’єктно-орієнтоване програмування (ООП) з принципами інкапсуляції (приховування внутрішньої реалізації для захисту даних), наслідування (створення нового класу та основі вже існуючого – батьківського), поліморфізму (здатність виконувати одну і ту саму дію різними об’єктами по-своєму) та абстракції (виділення найважливіших характеристик об’єкта) дуже популярне у C++ через роботу з класами, об’єктами, атрибутами або полями, та методами.
     Однак об’єктно-орієнтований підхід у C++ має свої переваги та недоліки, які диференціюють його від інших мов. Це такі особливості:
* множинне наслідування. На відміну від мов програмування, в яких клас не може успадковувати властивості одразу від кількох батьківських класів, таких як Java чи C#, Класи у C++ можна успадковувати декілька разів;
* відсутність Garbage Collector’а (збирача сміття). Керувати пам’яттю потрібно або розробнику механічно, або автоматично, через розумні вказівники (unique_ptr, shared_ptr);
* складність проєктування. Ще до написання коду потрібно розуміти, як це буде працювати, що вимагає навичок архітектора. Якщо система побудована без такого усвідомлення, вона наповнена надлишковими абстракціями, інтерфейсами та класами, де можна було використали лише кілька простих функцій. Тоді код стає важким для розуміння.

#include <iostream>
#include <vector>

class ScoreCalculator {
public:
    ScoreCalculator(int bonusLimit) : bonusLimit_(bonusLimit) {}

    int CalculateTotal(const std::vector<int>& scores) const {
        int totalScore = 0;

        for (int score : scores) {
            if (score > bonusLimit_) {
                totalScore += score * 2;
            } else {
                totalScore += score;
            }
        }
        return totalScore;
    }

private:
    int bonusLimit_;
};

int main() {
    const std::vector<int> userScores = {30, 60, 45, 80};
    
    const ScoreCalculator calc(50);

    std::cout << “Total score: “ << calc.CalculateTotal(userScores) << “\n”;
    return 0;
}

3.4.3. Узагальнене програмування
     Узагальнене програмування у C++ полягає в написанні коду, незалежного від типу даних. Основною перевагою цієї парадигми програмування є можливість використовувати один код для різних типів без втрати безпеки та продуктивності (якщо код написано правильно).
     Основними принципами такого програмування згідно з рекомендаціями є
* шаблони. Вони використовуються для підвищення рівня абстракції алгоритмів. Для простих типів прийнято використовувати абстрактні імена шаблонних параметрів (T, U), а для складних – назви з великої літери (Container, Iterator);
* концепти. Якщо при компіляції коду відбудеться помилка – компілятор виведе багато незрозумілого тексту. Щоб цього запобігти, потрібно використовувати requires вирази (див. рис. 3.9) для явного обмеження типів.

#include <iostream>
#include <vector>
#include <concepts>

template <typename T>
requires std::isArithmeticV<T>
T calculateTotalSum(const std::vector<T>& items) {
    T total = 0;
    for (const auto& item : items) {
        total += item;
    }
    return total;
}

int main() {
    std::vector<int> intNumbers = {10, 20, 30, 40};
    std::cout << “Integer sum: “ << calculateTotalSum(intNumbers) << “\n”;

    std::vector<double> doubleNumbers = {5.5, 2.1, 3.4};
    std::cout << “Double sum: “ << calculateTotalSum(doubleNumbers) << “\n”;

    return 0;
}

     На противагу плюсам, цей підхід має і свої недоліки. Основні це:
* складність. Написання універсального коду може здаватися легкою задачею, але часто це не так. Параметри з абстрактними назвами ускладнюють написання;
* незрозумілі помилки компілятора. Якщо під час компіляції станеться помилка, згенерується гігантський заплутаний текст від компілятора, який буде важко розібрати.
3.4.4. Рекомендації та обмеження
     Угоди про написання коду рекомендують використовувати описані вище та інші парадигми програмування за такими принципами:
* уніфікація. Коли кожен з розробників великої команди пише з одною (чи декількома) парадигмою, код стає легшим для розуміння колегами;
* продуктивність. Використання коректної парадигми, яка підходить до завдання, дозволяє уникати накладних витрат при виконанні програми. Наприклад, буває краще замінити динамічний поліморфізм віртуальних функцій та статичний поліморфізм за допомогою шаблонів;
* масштабованість. Дотримання чітко встановлених правил щодо застосування парадигм програмування допомагає прибрати хаос у коді.
     Однак, поганою практикою є зловживання принципами програмування, через що програма стає працювати повільніше або навіть з помилками. Не треба використовувати глибокі ієрархії успадкування класів (більше 3 рівнів), якщо це не обов’язково, бо віртуальні функції мають накладні витрати і погіршують роботу кешу. Замість змішування імперативного стилю з старими глобальними змінними та масивами у стилі C рекомендовано інкапсулювати та мінімізувати області видимості. Також, якщо цикли критичні до продуктивності, краще використовувати статику або шаблони.
     Існує багато інших прикладів застосування та обмеження використання різних парадигм програмування. Найкращою стратегією буде комбінувати процедурну парадигму з об’єктно-орієнтованим підходом та узагальненим програмуванням.
3.5. Сучасні стандарти
     Найпершим офіційним стандартом плюсів є версія C++98, випущена понад 27 років тому [6]. З тих часів на шляху розвитку мови вийшло багато стандартів: C++11, C++14, C++17, C++20, C++23 та найновіший на сьогодні, C++26. Кожен з них додав свої можливості та технології як частину великої мови.
     До появи C++11 мова майже не оновлювалася більше 10 років, завдяки чому з’явилися та активно додавали новий функціонал інші, кращі на той час, мови, такі як C#, Go та Rust. В той час старий C++ вимагав написання багато рядків низькорівневого коду що призводило до багів. Після розуміння цього комітет ISO та Б’ярне Страуструп (розробник C++) [7] спільними зусиллями створити революційний стандарт, який надав нове життя давній мові програмування.
     Сучасним кодом C++ (Modern C++) вважається використанням стандартів, починаючи з версії С++11 і далі до 17 або 20 версій, замість архаїчного C++98 з його конструкціями у стилі C, писати на якому вкрай не рекомендується. Фундаментом сучасної мови є одинадцята версія, який варто розглядати як базовий мінімум. Сучасним стандартом та найкращим вибором для проєктів де-факто є двадцята версія, яка принесла зміни, які полегшують написання коду. Розберемо основні аспекти багатозгадуваного стилю.
3.5.1. Виведення типів
     Опис: раніше розробники явно прописували деколи довгі та складні типи, особливо для ітераторів та шаблонів. У сучасному C++, а точніше у версії C++, замість прямого зазначення типу даних додано ключові слова auto (див. рис. 3.10) та decltype (див. рис. 3.11). Перше слово дозволяє вивести тип під час компіляції на основі значення, що присвоюється – це робить код гнучкішим до рефакторинґу, а друге – скорочення від declaration type – наказує компілятору визначити тип даних на основі результату виконання виразу в дужках.

auto a = 3.14; // double
auto b = 1; // int
auto& c = b; // int&
auto d = new auto(123); // int*
auto x; // помилка: ‘x’ потребує ініціалізації
Рисунок 3.10 – Приклад використання ключового слова auto
(складено автором на основі даних [8])
     Ключове слово auto не робить C++ динамічно типізованої мовою, оскільки воно працює лише під час компіляції. Витрат на визначення типу під час виконання програми немає, на відміну від Python чи JavaScript. 

template <typename X, typename Y>
auto add(X x, Y y) ? decltype(x + y) {
    return x + y;
}

int main() {
    add(1, 2); // 3
    add(1, 2.0); // 3.0
    add(1.5, 1.5); // 3.0
}

(складено автором на основі даних [8])
     
     Хоча у стандарті C++14 компілятор навчили виводити результат самостійно, без використання decltype. Достатньо написати auto add(X x, Y y).
3.5.2. Керування типами
     Опис: стандарти сучасного C++ рекомендують уникати приведення типів у стилі C (див. рис. 3.12), оскільки воно є небезпечним та ускладняє читання коду. Використання такого приведення може випадково зняти константність або перетворити несумісні вказівники без жодного попередження від компілятора, а результаті чого програма може впасти у рантаймі. Безпечно буде використовувати такі оператори:
* static_cast – перетворення під час компіляції сумісних типів;
* dymanic_cast – приведення по ієрархії успадкування класів (вниз по дереву). Якщо приведення неможливе – повертає nullptr;
* const_cast – зняття або додавання константності;
* bit_cast – перетворення несумісних типів (з’явився у C++20)

double pi = 3.14;
int a = (int)pi; // втрата точності
const int X = 10;
int* p = (int*)&X; // зняття const без попередження
Рисунок 3.12 – Приведення типів в стилі C

double pi = 3.14;
int a = static_cast<int>(pi); // безпечне перетворення
const int X = 10;
const int* p = &X; // константність зберігається
Рисунок 3.13 – Безпечне приведення типів

     Сучасні стандарти створюються для підвищення безпеки коду – зменшення кількості помилок при роботі з пам’яттю; спрощення читання та підтримка позбавленням розробників від шаблонного коду; збільшення продуктивності, віддаючи компілятору складності керування ресурсами; та надання компілятору інформації для оптимізації.
3.5.3. Керування пам’яттю
     Опис: безпечне керування пам’яттю мінімізує ризик виникнення помилок, пов’язаних із виділенням та звільненням пам’яті: витоки пам’яті, завислі вказівники, подвійне звільнення та невизначена поведінка.
     У старому C++ розробник самостійно керує пам’яттю за допомогою операторів new/delete, що вимагає обачності: кожне виділення пам’яті обов’язково повинно мати своє delete для її звільнення. У сучасному C++ розробник більше не звільняє пам’ять вручну.
     Головним принципом безпеки у C++ є паттерн RAII (Resource Acquisition Is Initialization). Його суть в тому, що одержання ресурсу пов’язане з ініціалізацією об’єкта, а його звільнення відбувається автоматично в деструкторі цього об’єкта під час виходу з області видимості. Тобто, коли об’єкт знищується, його деструктор викликається автоматично і очищає пам’ять.

#include <iostream>

class ResourceHandler {
private:
    int* data;
public:
    ResourceHandler(size_t size) {
        data = new int[size];
    }

    ~ResourceHandler() {
        delete[] data;
    }

    // Заборона копіювання, захист від подвійного видалення
    ResourceHandler(const ResourceHandler&) = delete;
    ResourceHandler& operator=(const ResourceHandler&) = delete;
};

int main() {
    {
        ResourceHandler res(1);
        // Використання ресурсу
    } // вихід з області видимості. Деструктор викликається автоматично

    return 0;
}
Рисунок 3.14 – Приклад використання концепції RAII

     Наступною рекомендацією є використання розумних вказівників зі стандартної бібліотеки <memory>:
* unique_ptr. Єдине володіння ресурсом. Лише один вказівник може володіти об’єктом. Його не можна скопіювати, але можна перемістити (за допомогою move). Коли він знищується, пам’ять очищується автоматично;
* shared_ptr. Спільне володіння ресурсом. Підраховує посилання. Пам’ять звільнюється коли знищується останній вказівник, який на неї посилався;
* weak_ptr. Невласницький вказівник. Працює спільно з попереднім та використовується для запобігання циклічних посилань – коли об’єкти посилаються один на одного і не можуть видалитися.

#include <iostream>
#include <memory>

Struct Resource {
    Resource() { std::cout << “Created\n”; }
    void action() { std::cout << “Working…\n”; }
    ~Resource() { std::cout << “Deleted\n”; }
};

int main() {
    std::unique_ptr<Resource> ptr1 = std::make_unique<Resource>();
    ptr1->action();

    {
        std::shared_ptr<Resource> ptr2 = std::make_shared<Resource>(int);
        std::shared_ptr<Resource> ptr3 = ptr2;
    } // ptr2 та ptr3 знищуються, пам’ять звільняється автоматично

    return 0; // ptr1 знищується при завершенні програми

3.6. Оптимізація продуктивності
     Оптимізація продуктивності це сукупність стандартів та правил, узгоджених у команді, які спрямовані на написання ефективного коду, який вимагатиме відносно небагато ресурсів, ще на етапі його створення.
     На відніму від загального Cove Convention, який відповідає за стиль форматування, його продуктивний компонент регламентує застосування мовних конструкцій. Він визначає, як розробники мають працювати з пам’яттю, передавати параметри в функції та використовувати можливості сучасного C++ для запобігання накладних витрат.
     Команда пише код в єдиному стилі, що мінімізує повільні операції або створення зайвих копій об’єктів. Чіткі правила надають компілятору більше інформації для оптимізації. Код, оптимізований за обговореними стандартами, залишається чистим, читабельним, зрозумілим та легко підтримуваним для інших членів команди. Також рев’юєрам буде легше помітити архітектурні чи продуктивні проблеми.
     В угоду про написання продуктивного коду часто входять управління пам’яттю, ефективні алгоритми та структури даних та робота з БД.
     Управління пам’яттю та ресурсами включає: контроль витоків пам’яті – обов’язкове закриття потоків, з’єднань з БД, файлових дескрипторів; ефективне виділення пам’яті – заборона створювати зайві об’єкти в циклах, домовленість про повторне використання об’єктів для ділянок з високим навантаженням та роботу з рядками. Також сюди можна віднести передачу параметрів, коли прості типи передаються за значенням, а складні – за константним посиланням або вказівником, щоб уникнути дорогого за часом копіювання, та заборону або обмеження використання купи (heap) у циклах, і заміна їх на стекові структури.
     Ефективними алгоритмами та структурами даних вважаються ті, які виконують потрібну складну дію дуже швидко. Це може бути пошук елемента у set, що виконується за час O(1), яке при використанні list займає O(n) часу. Таких випадків багато, і часто підходящими є різні структури даних.
     Щодо роботи з базами даних, можуть бути присутні такі домовленості, як заборона виконання SQL-запитів всередині циклів, обмеження вибірки з БД або вибір лише тих колонок, які потрібні для бізнес-логіки (заборона на використання SELECT* без потреби).
     Іншими можливими домовленостями можуть стати: асинхронність, паралелізм та мереживі запити – кешування, використання пулу потоків; застосування ключових слів для оптимізації компіляції, таких як (noexcept для функцій, що гарантовано не викликають виключень, constexpr і consteval для константних значень та inline для маленьких функцій).
     За Code Convention, застосовувати оптимізацію продуктивності рекомендовано у:
* модулях з високими вимогами до продуктивності – рендеринг, драйвери, вбудовані системи;
* бібліотечному коді та фреймворках, де код виконується тисячі разів, мусить мати мінімальні накладні витрати;
Не варто ж використовувати оптимізацію в таких випадках:
* бізнес-логіка з низьким навантаженням – панелі адміністратора, засоби конфігурації, одноразові скрипти, де швидкість роботи не впливає на досвід користувача;
* коли структура програми ще постійно змінюється. На етапі прототипування обмеження можуть сповільнити розробку та ускладнити рефакторинґ;
     Щоб правила оптимізації реально працювати, їх варто автоматизувати або інтегрувати у процес розробки. Це можна зробити шляхом використання лінтерів на кшталт Clang-Tidy або інтеграції в CI/CD – автоматичний запуск тестів продуктивності. І головне, що оптимізації мають базуватися на результатах профілювання, а не на припущеннях.
3.7. Обробка помилок
     У великих проєктах на C++ є безліч способів повідомити про помилку – винятки, коди повернення, аварійне завершення. Якщо кожен розробник полюбляє та використовує свій підхід, код перетворюється на безлад. Обробка помилок не це не лише вибір технічного інструмента, а єдиний для команди набір правил, як програма повинна сигналізувати про нестандартні ситуації.
     Ряд чітких стандартів розв’язує такі завдання допомагає розробникам одразу зрозуміти, чого очікувати від функції – винятку чи коду помилки. Узгоджений всередині команди підхід допомагає уникнути витоків ресурсів під час аварійного завершення та спрощує тестування.
3.7.1. Винятки для аномалій
     Винятки (throw) це механізм сигналізації про те, що функція не здатна виконати своє завдання через виняткову ситуацію. Вони потрібні щоб зробити обробку помилок надійною і неможливою для ігнорування, водночас відокремленою від коду бізнес-логіки.
     Винятки потрібно використовувати тільки для помилок та нештатних ситуацій (аварій, збоїв, неможливості виконати задачу): неможливість відкрити файл, зникнення зв’язку з БД, нестача RAM, передача неприпустимих аргументів та інші випадки. Найкраще такі винятки проявляють себе у конструкторах, оскільки останні не мають типу повернення, винятки стають єдиним надійним способом повідомити про неможливість ініціалізувати об’єкт. Не треба заміняти ними повернення через return або додавати у цикли.

#include <iostream>
#include <stdexcept>

double divide(double x, double y) {
    if (b == 0.0) {
        throw std::invalid_argument(“Error: divide by 0!”);
    }
    return a / b;
}

int main() {
    try {
        double result = divide(10.0, 0.0);
        std::cout << “Result: “ << result << “\n”;
    } catch (const std::exception& e) {
        std::cout << “Exception: “ << e.what() << “\n”;
    }
}
Рисунок 3.16 – Приклад використання винятків у нештатних ситуаціях
     
     Виключення потрібно ловити за константним посиланням – це запобігає зайвому копіюванню. Винятки обов’язково повинні бути прив’язані до паттерна RAII – це гарантує відсутність витоків пам’яті під час розгортання стека. Також винятки повинні використані у конструкторах для обробки помилки при створенні об’єкта, та ніколи не повинні бути присутніми у деструкторах – через них програма може впасти.
3.7.2. Винятки для нормальних ситуацій
     Якщо відсутність результату це не помилка, а передбачуваний сценарій бізнес-логіки, наприклад, пошук користувача в БД за ID, використання винятків може бути надлишковим. У такому разі рекомендовано використовувати optional. Воно гарантує необов’язковість поля у структурі даних або аргументах функції.

#include <iostream>
#include <optional>
#include <string>

std::optional<std::string> findUserById(int id) {
    if (id == 15) {
        return “John”;
    }
    return std::nullopt;
}

int main() {
    auto user = findUserById(100);
    
    if (user.has_value()) {
        std::cout << “User “ << *user << “\n”;
    } else {
        std::cout << “User with this ID does not exist.\n”;
    }
}
Рисунок 3.17 – Приклад використання винятків для нормальних ситуацій
     
     Для обрання командою методів обробки помилок можна виділити декілька основних моментів. Спочатку потрібно визначитися, чи дозволені взагалі винятки в проєкті: якщо так – з’ясувати, де їх можна кидати, а де заборонено (наприклад, у конструкторах чи певних модулях). У функціях, де помилка є частиною бізнес-логіки, краще використовувати expected. Код конвенція обов’язково повинна забороняти ігнорування кодів повернення.
3.8. Коментування та документація
     Коментарі абсолютно необхідні для читабельності коду. Коментування це не лише спосіб пояснення щось для себе, а частина розробки, яка пояснює, чому використовується саме цей алгоритм, а не інший, як користуватися класами та функціями без заглиблення в реалізацію, та, іноді, попереджає про небезпеку. Якщо код говорить як це зроблено, то коментарі пояснюють, чому саме таке рішення обрано.
     Коментувати рекомендовано неочевидні оголошення класу або структури, пояснюючи для чого вони призначені та як їх слід використовувати. Коментарі класу повинні надавати читачу інформацію, як і коли використовувати клас, а також додаткові міркування для правильного використання.
     Майже кожне оголошення функції повинно мати коментарі перед ним, в яких описується, що робить функція та як її використовувати. Такі коментарі можна пропустити, якщо функція проста та не робить нічого неочевидного. У коментарях до оголошення функції слід згадати вхідні та вихідні дані, параметри та їхні обмеження і як вони обробляються. У коментарі до визначення функції потрібно додати пояснення складної частини коду та хитрощів кодування, можливо навіть з ASCII схемою.
     Не потрібно описувати у коментарях очевидне, що робить код та вже задокументований раніше код, що заплутує команду. При написанні коментаря, найкраще вважати, що читач добре розуміє C++.
     Коментарі повинні бути написані добре з точки зору пунктуації, орфографії та граматики, що допомагає підтримувати високий рівень ясності та читабельності. Це має бути наче розповідний текст. У сучасній розробці стандартом є англійська мова, навіть якщо команда розмовляє іншою мовою, оскільки в проєкт можуть бути залучені іноземні спеціалісти.
     Золотим стандартом є стиль коментування Doxygen [9]. Він автоматично аналізує вихідних код і генерує готову документацію у різних форматах. Doxygen використовує спеціальний синтаксис коментарів. Замість звичайних, використовуються потрійні слеши (///) або спеціальні блоки (/**…*/). Інтеграція Doxygen у систему збірки, таку як CMake, дозволяє автоматично оновлювати документацію при кожному оновленні коду (коміті).
